# DSH 插件仓库的"规范驱动"工作流选型结论

> 调研范围：DSH 官方仓库 `/Users/golddream/code/git-public/deepseek-harness`（只读）+ 外部 OpenSpec 生态
> 目标场景：一个**独立的 DSH 客户端插件仓库**（`rate-dsh-lumina`），已有 12 份中文设计文档，需要从零开始工程化

---

## 一、结论先行

### 推荐：**DSH 原生 Agent Note 约定 + 一个 DSH Skill**（不引入 OpenSpec）

具体形态：

1. 在 `rate-dsh-lumina/.agents/notes/` 复刻 DSH 官方的 **Agent Note 树**（`proposed/` / `implemented/` / `rejected/` × 6 个 class + 编号 + 模板 + 门禁脚本）。
2. 把 lumina 自己的开发规范做成一个 **DSH Skill**：`.agents/skills/dsh-lumina-dev/SKILL.md`，让 DSH 原生加载、模型按需调用。
3. 12 份中文设计文档**不被重写**，而是按语义拆解、映射进 Agent Note 树（见下文"迁移映射"）。

### 为什么是它

| 判据 | DSH Agent Note + Skill | OpenSpec | Spec-Kit / BMAD |
|---|---|---|---|
| 是否 DSH 官方自己的答案 | ✅ 就是（`.agents/notes/` 845 份在用） | ❌ 外部工具 | ❌ 外部工具 |
| 12 份**中文**文档能否直接安置 | ✅ 契约明文允许「Chinese-first Agent Note」 | ⚠️ 需改写成 Requirement/Scenario + ADDED/MODIFIED/REMOVED delta 英文式结构 | ⚠️ 同上 |
| 在 DSH 客户端里能否直接用 | ✅ Skill 原生被 `ctx.skills` 发现、模型可调 | ❌ 无 `dsh` adapter，命令文件落在 `.claude/commands/opsx/*.md` 等 DSH **不读**的目录 | ❌ |
| 是否引入第二套 spec 大本营 | ❌ 不会 | ⚠️ `openspec/specs/` 与 12 份中文文档必然双轨漂移 | ⚠️ |
| 机器门禁 | ✅ `verify-agent-note-format` + 分类门 + 双语配对门 | ✅ `openspec validate` | ✅ |
| 额外运行时依赖 | 无 | Node ≥20.19.0 的全局 CLI | Spec-Kit 需 Python |
| 规模适配 | 单插件 / 单仓 ✅ | 单仓 ✅ 但偏重 | ❌ 偏重（5 相位 / 12–21 persona / ~31k token 每轮） |

一句话：**OpenSpec 解决的是"通用 AI 编程的规范缺失"，而 DSH 已经自带了一套成熟、机器门禁、双语原生、并且能直接挂进 DSH Skill 机制的规范体系。** 对一个 DSH 客户端插件仓库，选 DSH 原生 = 零集成成本、零翻译损耗、零双轨漂移。

### 不推荐 OpenSpec 的具体理由（4 条）

1. **客户端集成缺口**：OpenSpec 的 30+ adapter 全部写进**各工具专属目录**（`.claude/commands/opsx/<id>.md`、`.cursor/commands/opsx-*.md`、`.github/prompts/opsx-*.prompt.md`…）。DSH 只读 `.dsh/skills/<name>/SKILL.md` 与 `.agents/skills/<name>/SKILL.md`（一层深），**没有 `dsh` / `deepseek-harness` adapter**。要跑 `/opsx:propose` 必须手工桥接一遍，等于自己写 OpenSpec 的 adapter。
2. **格式与已有 12 份中文文档正面冲突**：OpenSpec 的 spec 是 `### Requirement:` + `#### Scenario:` + GIVEN/WHEN/THEN 的**行为契约**体裁，delta 体裁是 `## ADDED/MODIFIED/REMOVED Requirements`。而 12 份文档是**中文设计散文**（定位/架构/动效规格/实施路线/风险）。要迁进 `openspec/specs/`，等于把已有中文资产重写一遍并丢掉中文优先的作者体验。OpenSpec 有 `--language` 选项与 `docs/multi-language.md`，但那解决的是**翻译**，解决不了**体裁**。
3. **双轨漂移**：采用后仓库里同时有 `openspec/specs/`（英文契约体）与 12 份中文设计文档两套"真相源"。DSH 的 Agent Note 体系用**单一路径编码 + 机器门禁 + 归档策略**专门避免这件事；引入 OpenSpec 反而把 DSH 已经解决的问题重新引进来。
4. **重量与依赖**：为一个"五处动效"的插件引入全局 Node CLI、6 个生成 skill、`config.yaml` + `specs/` + `changes/` + `changes/archive/` 四级目录，边际收益为负。

> **保留意见（何时该重新考虑 OpenSpec）**：如果 lumina 未来扩成**多包/多仓**、有 3 人以上团队、需要"规格 delta 历史 + 跨工具（Claude Code / Cursor / Codex）共享同一份规格"，那时 OpenSpec 的 delta 模型和 archive 审计轨迹才真正兑现价值，届时迁移成本也低（它产出的就是纯 Markdown + JSON）。

### 不推荐另外两个的简述

- **GitHub Spec-Kit**：greenfield-first、constitution 驱动、5 相位、**需要 Python**。lumina 的"宪法"就是 DSH 的 `AGENTS.md` + 本仓 `AGENTS.md`，直接引用即可，不必再造 constitution 层。
- **BMAD-METHOD**：12–21 个 AI persona、PRD→架构→故事→代码的完整 PM 流水线、**实测 ~31,667 token/轮、$800–$3,200/开发者/月**，同一任务 OpenSpec 12 分钟 / Spec-Kit 90 分钟 / BMAD 5.5 小时。与"5 个动效"完全不成比例。
- **Claude Taskmaster**：本质是 **PRD → `tasks.json` 的任务清单器**（36 个 MCP 工具），**不产出 spec / design / delta**，而且需要 MCP 客户端 + API Key。它要解决的问题 DSH 自己的 `todo_write` / Task Board 已经解决了。
- **CCPM（automazeio/ccpm）**：PRD→Epic→**GitHub Issues**→Code，靠 Git worktree 并行。思路（PRD 拆 epic 再拆 issue）值得借鉴，但依赖 GitHub Issues + 多 worktree 基础设施，对单插件仓库过重，且与 DSH 内建的 Team/subagent/task 机制重复。
- **Todoist-MCP**：只是个人 todo 同步，与规格工作流无关。

#### A.1.1 目录分层规则：两条轴，都编码在**路径**里

#### A.1.2 文档模板：front-matter、标题格式、编号规则

**这不是 YAML front-matter**，DSH 用的是**固定的前三行 header block**。`.agents/notes/README.md:60-74`：

```markdown
# Agent Note: <title>

Status: <status>
```

`Status:` 三种形态，且**必须与所在 lifecycle 文件夹一致**（门禁会交叉校验）：

- `Status: proposed`
- `Status: implemented`
- `Status: rejected — <why, in one line>`

> The status carries no dates and no parentheticals: the filename holds the first-proposed date, git holds everything else…

**编号规则**：文件名 `yyyy-mm-dd-topic-title.md`，`topic-title` 为 kebab-case。**日期是"该议题首次被提出"的日期**（依据 git 历史），不是决策日期。`.agents/notes/README.md:17`：

> The date in the filename is when the topic was **first proposed** (per git history). Cross-references between Agent Notes use relative markdown links (`[topic](../../implemented/architecture/2026-…-….md)`) — never bare prose or numbers — so they are mechanically checkable and survive moves between folders.

**正文骨架按 lifecycle 分化**：

`proposed/`（`.agents/notes/README.md:82-89`）：

```markdown
## Problem
## Proposal
…bespoke sections…
## Alternatives considered
## Acceptance criteria
## Risks
```

`implemented/`（`.agents/notes/README.md:95-101`）：

```markdown
## Problem
## Decision
…bespoke sections…
## Alternatives considered
## Consequences
```

`rejected/`：冻结提案时的章节原样保留，判决写在 `Status:` 行上。

**硬性规定**：

- `## Alternatives considered` —— **每份 note 必填**。`.agents/notes/README.md:111`：「A decision recorded without what it beat invites re-litigation — the failure Agent Notes exist to prevent.」
- `implemented/` 里**禁止**出现提案期标题（`## Proposal` / `## Plan` / `## Migration plan` / `## Acceptance criteria`），门禁直接拒绝
- 允许 `## Testing` / `## Deferred` / `## Related` 等"现在时事实"章节
- 2026-07-05 之前的 note 若 alternatives 无法从记录重建，可用哨兵注释放行：

#### A.1.3 中文版 `.zh.md` 约定与 `.i18n.yaml` 的作用

**三元组约定**（`/Users/golddream/code/git-public/deepseek-harness/docs/i18n/README.md`）：

> **A pair is three sibling files.** The English `foo.md`, the Chinese `foo.zh.md`, and a consistency record `foo.i18n.yaml`, all in the same directory. No locale directories, no separate translation repo, no interleaved bilingual files. **Pairs merge whole: a PR never lands one language without the other two files.**

**`.i18n.yaml` = 双语一致性记录，存的是两侧的 git blob hash**。实例 `/Users/golddream/code/git-public/deepseek-harness/.agents/notes/README.i18n.yaml`：

```yaml
# Bilingual-pair consistency record (docs/i18n/README.md): the git blob hash of each
# side as of the last confirmed-consistent state. Both languages carry equal authority;
# after editing either side, bring the other along and re-record with:
#   pnpm run verify-translation-pairing --write .agents/notes/README.md
README.md: ae8e4724d610c97d74910d7dec5c95af69e93281
README.zh.md: 8cecc7068d9efc5e2ebb78d2301d03633f70f137
```

要点：
- 存 **blob hash**（不是 commit hash），所以"同一个 PR 里改了两侧"也能算出；一致性 = 纯内容比较
- 记录可通过 `refs/dsh/translation-pairing/snapshots/` 找回上次确认的确切文本，因此**打补丁式最小更新**即可，不必整篇重译
- 重录命令：`pnpm run verify-translation-pairing --write <pair>`；`--write` 强制要求点名你确认过的 pair（`--write --all` 是全库形式）
- 门禁 `pnpm run verify-translation-pairing` 属于 `doc-sync`；CI 也会跑

**中文侧的机器校验 token 保持英文原样**（`.agents/notes/README.md:125`）：

> A `.zh.md` counterpart mirrors its English sibling's structure section-for-section under the [i18n contract](../../docs/i18n/README.md); the machine-checked header tokens (`# Agent Note: ` and the `Status:` line) stay in English verbatim. The format gate skips `.zh.md` files — the pairing gate checks their consistency.

**结构镜像要求**（`docs/i18n/README.md`）：标题层级与顺序、列表种类、序号起点、列表项数量、表格行列数、链接目标（含 query/fragment 后缀）、verbatim code block 必须一一对应；中文侧必须在 H1 后紧跟 `[English](foo.md) | 中文` 回链。

**⭐ 对 lumina 决定性的一点** —— `docs/i18n/README.md` 明确：

> **Both languages carry equal authority.** A document may be authored and reviewed in either language first — **a Chinese-first Agent Note is as legitimate as an English-first one** — and the counterpart is translated from it. Neither file outranks the other.

**DSH 官方双语 Agent Note 是被明确许可的**。这直接决定 lumina 12 份中文文档可以原生落地。

#### A.1.4 AGENTS.md 里"写代码前要不要先写 spec/设计文档"的原文

**根 `AGENTS.md:123`**（`/Users/golddream/code/git-public/deepseek-harness/AGENTS.md:123`）：

> - **Non-trivial changes MUST include an Agent Note in the same PR;** only mechanical/local edits are exempt ([scope](.agents/notes/README.md#when-to-write-one)). Archived notes are frozen: never edit or treat them as current authority ([archive policy](.agents/notes/README.md#archiving-and-deletion)).

**`.agents/notes/README.md:46`**（更完整的口径）：

> Every non-trivial change MUST add or update at least one Agent Note in the same PR. A change is non-trivial when it alters behavior, architecture, a contract shared across files or packages, process or tooling, testing strategy, an on-disk, wire, or configuration format, or another decision a maintainer may reasonably revisit. **A proposal for substantial future work starts in `proposed/`; a decision already made starts in `implemented/`.** Pick the class folder that matches the decision (see [Classification](#classification)).

**`.agents/notes/README.md:5`**（定义）：

> One kind of design doc lives here. An **Agent Note** records a decision or proposal that affects this codebase — the *why* and *what we gave up*, the parts code and docs can't carry.

**`.agents/notes/AGENTS.md:3`**（把 Agent Note 直接类比为 RFC）：

> Agent Notes are effectively RFCs written by agents: durable proposals and decision records that preserve rationale, alternatives, consequences, and required verification.

#### ⚠️ 精确解读：DSH 的规则是"**PR 耦合**"，不是"**代码前强制**"

这一点必须说清楚，否则会误用：

- **没有**任何门禁检查"你必须先写 note 才能写代码"。门禁只检查 **note 的格式**（`verify-agent-note-format`）、**分类闭合**（`agent-note-tree.ts`）、**双语配对**（`verify-translation-pairing`）——**都不检查代码与 note 的先后**。
- 真正"spec 先行"的机制是**生命周期**：`proposed/` → `implemented/` 的迁移。`.agents/notes/README.md:121` 规定了迁移时必须同步改写：

> Moving a file between lifecycle folders means updating the `Status:` line and re-satisfying that folder's skeleton in the same change — the gate fails the move otherwise. Concretely, `proposed/` → `implemented/` rewrites `## Proposal` into a present-tense `## Decision`, folds `## Acceptance criteria` and `## Risks` into `## Consequences` (or a present-tense `## Testing`/`## Verification` section for what now pins the behavior), and drops plans in favor of what shipped…

- **所以正确用法是**：动手前在 `proposed/{class}/` 落一份提案（含 `## Acceptance criteria` / `## Risks`）；落地时把它移到 `implemented/{class}/` 并按规则改写。这样"spec 先于 code"是**纪律**而非**门禁**。
- **补充义务**：`implemented/AGENTS.md` 要求已发布的 note **随代码同步更新事实**（路径、符号、默认值、机制），但**不得改写决策本身**：

> Update factual realization in place. A reversal of the decision or its rationale requires a new Agent Note and cross-link…

#### A.1.5 归档 / 淘汰纪律（决定仓库不会无限膨胀）

- 归档条件：决策已完整且其 rationale 不太可能再指导未来工作
- **永不归档 `proposed/`**（"reject an obsolete proposal"）
- `rejected/` 只在"能防止一次可能的错误"时保留，否则**三件套（英 + 中 + sidecar）一起删**
- 归档是路径编码的 `archived/{class}/…`，内容**只允许**加一行 `Archived: YYYY-MM-DD`（紧跟 `Status:` 之后，中英两侧都加），并重录 sidecar、修/删入链
- 封存后**永久冻结**："Do not edit, translate, reformat, update, move, or delete it, and do not treat it as authority for current behavior."
- 专用校验器 `scripts/verify-archived-agent-notes.ts` 负责闭合类树、三件套完整、归档元数据、sidecar 哈希、追加式冻结清单
- rationale 归 `.agents/notes/implemented/process/2026-07-26-frozen-agent-note-archive.md`

### A.3 `packages/skill/`：DSH 的 Skill 机制 —— **能不能把 lumina 的开发规范做成一个 Skill？**

#### A.3.1 包结构

`/Users/golddream/code/git-public/deepseek-harness/packages/skill/`：

| 包 | 职责 |
|---|---|
| `skill/` (`@deepseek-ai/dsh-skill`) | **注册表**，拥有 `ctx.skills` 接口；与来源无关（本地文件 / 内嵌插件数据 / HTTP / 其它后端） |

## 三、任务 B：OpenSpec 调研结论

### B.1 它解决什么问题

> OpenSpec helps you and your AI coding assistant **agree on what to build before any code is written.** You describe the change, the AI drafts a short spec and a task list, you both look at the same plan, and then the work happens. No more discovering halfway through that the AI built the wrong thing.
> —— [OpenSpec Docs 首页](https://openspec.dev/docs)

**四条原则**（`docs/concepts.md`）：

```
fluid not rigid         — no phase gates, work on what makes sense
iterative not waterfall — learn as you build, refine as you go
easy not complex        — lightweight setup, minimal ceremony
brownfield-first        — works with existing codebases, not just greenfield
```

**对单仓库小项目的适配度**：**核心机制是适配的**（正是它的主场）：
- 零 phase gate，artifact 依赖图是"enablers, not gates"（`docs/concepts.md`：「Dependencies are enablers, not gates. They show what's possible to create, not what you must create next. You can skip design if you don't need it.」）
- 5 分钟初始化，无重型 setup
- brownfield-first，`openspec/specs/` 起步几乎是空的，靠 archive 累积
- 支持**自定义 schema**（artifact 依赖图），小项目可裁剪成只要 `proposal → tasks`

**但对 lumina 真正的短板不在机制，而在两处**：
1. **客户端集成**（无 dsh adapter，见 B.4）
2. **产物体裁与已有中文文档不匹配**（见 B.5）

### B.2 工作流长什么样

**默认（core profile）**：

```
/opsx:explore ──► /opsx:propose ──► /opsx:apply ──► /opsx:sync ──► /opsx:archive
   (optional)
```

**展开（expanded）**：

```
/opsx:new ──► /opsx:ff 或 /opsx:continue ──► /opsx:apply ──► /opsx:verify ──► /opsx:archive
```

`core` profile 含 `propose`、`explore`、`apply`、`update`、`sync`、`archive`；展开命令需 `openspec config profile` + `openspec update` 启用。

**命令在哪儿敲**（官方特别强调这是最常见的新手坑）：

> - `openspec ...` commands (like `openspec init`) run in your **terminal**.
> - `/opsx:...` commands (like `/opsx:propose`) run in your **AI assistant's chat**

**每个 change 文件夹的产物**：

| Artifact | 用途 |
|---|---|
| `proposal.md` | "why" 与 "what"——意图、范围、方法 |
| `specs/` | **delta spec**：`## ADDED` / `## MODIFIED` / `## REMOVED Requirements` + `#### Scenario:`（GIVEN/WHEN/THEN） |
| `design.md` | "how"——技术方案与架构决策 |
| `tasks.md` | 实现清单（带 checkbox 的 `## 1. …` / `- [ ] 1.1 …`） |

**产物依赖图**：

```
proposal ──► specs ──► design ──► tasks ──► implement
   ▲           ▲          ▲                    │
   └───────────┴──────────┴────────────────────┘
            update as you learn
```

**归档语义**（archive = delta 合并）：

> 1. **ADDED** requirements are appended to the main spec
> 2. **MODIFIED** requirements replace the existing version
> 3. **REMOVED** requirements are deleted from the main spec
>
> The change folder moves to `openspec/changes/archive/` for audit history.

**CLI**：`openspec init` / `openspec list` / `openspec show <change>` / `openspec validate <change>` / `openspec view`（交互式 dashboard）/ `openspec update` / `openspec config profile`。

### B.3 与"纯 Markdown 规格文档 + 任务清单"的差别

| 维度 | 纯 Markdown + 任务清单 | OpenSpec |
|---|---|---|
| 目录约定 | 无 | 强制 `openspec/specs/` + `openspec/changes/` + `changes/archive/` |
| 变更表达 | 整篇重写（漂移风险） | **delta**：`ADDED`/`MODIFIED`/`REMOVED`，合并语义确定 |
| 需求体裁 | 自由散文 | `### Requirement:` + `#### Scenario:` + GIVEN/WHEN/THEN，**可被 `openspec validate` 机械校验** |
| 生命周期 | 无 | `propose → apply → sync → archive`，archive = delta 合并 + 审计轨迹 |
| 上下文注入 | 无 | `config.yaml` 集中注入项目上下文（技术栈、约定）到各阶段 |
| 门禁 | 无 | `openspec validate` 格式校验；`/opsx:verify` 实现与 spec 对照（扩展 profile） |
| 产物可读性 | 自由 | 结构化，但**必须用 OpenSpec 的英文体裁** |

**核心差异 = "delta + 合并语义 + 归档审计轨迹"**。纯 Markdown 方案在 3–5 个文件规模时等价于手写模板；规模上去后，delta 机制才产生价值。

### B.4 Node/CLI 安装方式 & 客户端依赖

**安装**（Node.js **≥ 20.19.0**）：

```bash

cd your-project

```

**CLI 本身与客户端无关**，但**工作流是以"各客户端专属的命令文件"形式交付的**。30+ adapter，每个写自己的目录：

### B.5 其它候选工具横向对比

| 工具 | 核心形态 | 客户端依赖 | 语言/运行时依赖 | 适配 lumina？ |

| **BMAD-METHOD** | 12–21 个 AI persona，PRD→架构→故事→代码，三轨制（Quick/Standard/Enterprise） | Claude Code / Cursor / Codex / Copilot / Windsurf | Markdown agent-as-code | ❌ ~31k token/轮、$800–$3.2k/月、5.5h/任务 |

**各场景适配总结**：

- **已有代码库、要轻量变更管理** → OpenSpec
- **全新项目、要 constitution 驱动的强约束** → Spec-Kit
- **企业级、要完整 PM 生命周期 + 对抗式评审** → BMAD

- **DSH 插件仓库、要中文优先、要能被 DSH 加载** → **DSH Agent Note + DSH Skill**（本报告推荐）
